# ADR-0001: Multi-Team Architecture

## Статус
Принято

## Контекст
Система управления задачами должна поддерживать организационные команды для управления видимостью проектов. Разработчики должны видеть только проекты, назначенные их команде, с возможностью индивидуальных исключений.

## Решение
Внедрена мульти-командная архитектура с четырьмя новыми моделями:

### Модели данных
- `Team` — организационная команда
- `TeamMember` — участник команды с ролью (admin/lead/developer)
- `TeamProject` — назначение команды на проект
- `ProjectExclusion` — исключение пользователя из проекта

### Логика видимости
1. **Admin/Lead** — видят все проекты без ограничений
2. **Developer** — видят проекты где:
   - Они владелец проекта, ИЛИ
   - Они прямой участник проекта, ИЛИ
   - Их команда назначена на проект И они не в списке исключений

### API
- CRUD для команд и участников
- Назначение/отвязка проектов от команд
- Исключение пользователей из проектов
- Мягкое удаление пользователей (задачи становятся неназначенными)

## Альтернативы
1. **Простой RBAC** — роли без команд. Отклонено: не решает задачу организационной структуры.
2. **Иерархия команд** — команды в командах. Отклонено: избыточно для текущих требований.
3. **Теги проектов** — проекты с тегами для фильтрации. Отклонено: менее гибко, нет управления доступом.

## Последствия
### Положительные
- Гибкое управление видимостью проектов
- Поддержка организационной структуры
- Возможность индивидуальных исключений
- Сохранение данных при удалении пользователя

### Отрицательные
- Увеличение сложности схемы БД (+4 модели)
- Дополнительные API endpoints
- Необходимость синхронизации команд и проектов

## Решения по реализации
- PostgreSQL (не SQLite) для поддержки связей
- Транзакции при удалении пользователей
- `db push` вместо миграций для упрощения dev workflow
- Soft delete для пользователей (deletedAt)
