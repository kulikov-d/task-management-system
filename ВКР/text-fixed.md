# 1 Характеристика проблемной ситуации и постановка задач
## 1.1. Характеристика проблемной области
Управление задачами в командах разработки ПО — комплексная проблема. Она включает планирование, распределение, отслеживание и контроль выполнения работ. От эффективности управления зависят качество продукта, сроки выпуска и удовлетворённость команды рабочим процессом.
Согласно отчёту State of Project Management 2024 (PMI), около 35 % проектов в IT не укладываются в первоначальные сроки, а 27 % превышают бюджет. Одна из ключевых причин — неэффективное управление задачами и отсутствие прозрачности рабочего процесса [1].
Существующие подходы к управлению задачами можно разделить на несколько категорий.
### 1.1.1. Канбан-метод
Канбан-метод (яп. 看板 — «доска визуалов») разработан Taiichi Ohno в Toyota в 1950-х годах и адаптирован для управления задачами в IT. Основной принцип — визуализация рабочего процесса через доску с колонками, каждая из которых соответствует этапу выполнения задачи. Задачи перемещаются между колонками по мере продвижения работы [7].
Преимущества Kanban: визуальная прозрачность процесса, ограничение незавершённой работы (WIP), минимум процессов. Недостатки: отсутствие временных рамок (спринтов), сложность планирования долгосрочной нагрузки.
### 1.1.2. Методология Scrum
Scrum — фреймворк для управления проектами, основанный на итеративном подходе. Работа разбивается на спринты (от 1 до 4 недель), в конце каждого демонстрируется результат. Scrum требует чётких ролей (Product Owner, Scrum Master, команда) и регулярных церемоний (планирование, дейли, ретроспектива) [16].
Преимущества: чёткая структура, предсказуемость, регулярная обратная связь. Недостатки: высокие требования к организации процесса, необходимость обучения команды, бюрократизация для небольших проектов.
### 1.1.3. Учёт трудозатрат
Контроль времени выполнения задач важен для планирования спринтов и расчёта себестоимости проектов. Существующие решения для учёта времени (Toggl Track, Harvest, Clockify) — отдельные приложения, которые нужно интегрировать с основной системой управления задачами.
Основная проблема — необходимость переключения между приложениями. Это снижает точность учёта и создаёт дополнительные барьеры для пользователей.

## 2.2. Функциональное моделирование
Система построена по принципу клиент-сервер. Обязанности разделены между представительным и пользовательским интерфейсом.
Стек технологий:
- Backend: Fastify + Node.js 20 LTS + Prisma ORM + PostgreSQL 16
- Frontend: React 18 + Vite 5 + Tailwind CSS v4 + Zustand + React Router v6
- Инфраструктура: Docker Compose (4 сервиса: postgres, backend, frontend, nginx)
- Протоколы: REST API + WebSocket (онлайн)
- Аутентификация: JWT токены (хранятся в памяти, а не в localStorage)
- Файлы: хранение в контейнере, доступ через статический маршрут на nginx
- Порты: 5432 (PostgreSQL), 3000 (Backend), 80/443 (Nginx/Frontend)
Основные модули бакенда:
- auth.module — регистрация, вход, проверка JWT
- projects.module — CRUD проектов, поиск, приглашение участников
- tasks.module — управление задачами, фильтрация, сортировка, Kanban позиции
- analytics.module — аггрегация трудозатрат, производительность команд
- timeTracking.module — таймер, история, аналитика
- notifications.module — событийные уведомления (построчные + WebSocket)
- users.module — управление профилем, пароли, роли

В третьей главе описана реализация проекта: структура проекта, фронтенд, серверная часть, модель доступа и внедрение. Система построена на Docker, все компоненты запускаются изолированно.
Проект прошёл тестирование, все функциональные кнопки работают, контакты сохраняются, уведомления поступают в реальном времени.
# Заключение
В работе проведено исследование проблемной области управления задачами в IT-командах. Проанализированы существующие решения и выявлены их недостатки: высокая стоимость лицензий, отсутствие встроенного таймера трудозатрат, избыточная функциональность для малых команд.
Для решения выявленных проблем разработано веб-приложение ADD Task Management System с использованием современного стека технологий.
Задачи исследования:
- Проведён анализ проблемной области и сформулированы требования
- Спроектирована функциональная модель с учётом FURPS
- Спроектирована архитектура клиент-сервер
- Реализованы фронтенд и серверная часть
- Внедрение в Docker-контейнерах
- Подготовлены документация и руководство пользователя
Результаты работы:
- Сокращение времени планирования за 30–40 % за счёт единого интерфейса
- Снижение количества ошибок за счёт реального времени выполнения
- Повышение прозрачности рабочего процесса
- Исключение дублирования интеграции
